## A-1. コードが壊れていないこと（判定可能・自動）

```bash
cd tools/rtvc
python -m pytest tests/ -q      # 164 件 / 約 50 秒
```

| # | 条件 | 判定するテスト |
|---|---|---|
| 1 | テストが全件通る | 終了コード 0 |
| 2 | 音声デバイス・GPU 無しで通る | CI（GitHub Actions）で通っている＝証明済み |
| 3 | 窓とクロスフェードの算数が合っている | `test_passthrough_output_matches_the_exact_oracle` |
| 4 | アルゴリズム遅延に EXTRA が混入していない | `test_algorithmic_latency_is_block_plus_crossfade_only` |
| 5 | リングバッファが溢れたとき古い方を捨てる | `test_ring_buffer_drops_oldest_on_overflow` |
| 6 | リサンプラが申告どおりの遅延しか持たない | `test_stream_resampler_reports_its_true_latency` |
| 7 | tail 最適化が音を 1 サンプルも変えない | `test_tail_support_does_not_change_a_single_output_sample` |
| 8 | 10ms グリッド違反を起動時に弾く | `test_rvc_engine_refuses_an_off_grid_window_at_construction` |
| 9 | 無音ストリームが「満点」に見えない | `test_a_silent_stream_is_an_error_not_a_perfect_score` |
| 10 | warmup が本番と同じ窓長・同じ tail で走る | `test_warmup_uses_the_same_tail_as_the_live_loop` |

> **テストは 1ms のスケジューラ刻みを前提にする。** `conftest.py` がセッション全体で
> `timeBeginPeriod(1)` を握る。これが無いと Windows の既定 15.6ms 刻みで
> 「5ms のエンジンが 16ms」「2.67ms 周期のフィーダが 4 分の 1 の速度」になり、
> **コードは正しいのにテストだけ落ちる**（実際に `.venv-rvc` で 4 件落ちた）。

**#3 が中心。** passthrough なら出力は
「入力を X サンプル遅らせ、ブロック境界の X サンプルに等パワー窓の和を掛けたもの」に
**厳密に一致する**はず。聴感ではなく算数で判定している。

**#7 と #9 は実機で痛い目を見た項目の回帰テスト。**
#7 は速度最適化が音を変えていないことの担保、#9 は「全カウンタが 0 ＝ 完璧」に
見える最悪の壊れ方（排他モードのサイレント失敗）を検出する。

## A-5. RVC を載せたあと（判定可能・未実施）

前提：話者モデル `.pth` がまだ無い。`--engine rvc` は `exit=4` で正しく停止する。
作り方は [`VOICE_TRAINING.md`](VOICE_TRAINING.md)。

**訓練前に `python scripts\check_dataset.py <素材フォルダ>` が `合格` を出すこと。**
既存音源から作る場合は `prepare_dataset.py` で切り分けてから判定する。
素材が不合格のまま訓練すると、3 時間かけて悪いモデルができるだけ。

| # | 条件 | 合格ライン |
|---|---|---|
| 1 | `infer` | < 32ms（RTF < 1）。実運用は RTF 0.6 以下 |
| 2 | `under` / `over` / `drop` | すべて 0 |
| 3 | `eng.tail_aware` が `True` | tail が効いていないと約 3.4 倍のコストを払う |
| 4 | infer 計測に `torch.cuda.synchronize()` が入っている | 無いと**実際より小さく出る** |
| 5 | モデルの SR が 48k / 24k | 40k だと起動時に `RuntimeWarning`（20dB の損） |

### TOTAL 目標は再評価が必要

デバイス 46.67ms を受け入れた前提では

```
46.67 (device) + 40 (B+X) + infer + out-buf
```

なので **infer をほぼ 0 にしても 90ms 台**。当初の「口→仮想ケーブルで 100ms 以下」は
達成可能だが余裕がほとんど無い。**infer に使える予算は実質 10ms 弱。**

これを広げたい場合の選択肢は 2 つだけで、どちらも代償がある:

| 手段 | 得られるもの | 代償 |
|---|---|---|
| `B` を 30 → 20ms | 10ms | RTF が上がる（推論回数が増える） |
| 有線マイク **かつ** 入出力を別ストリーム化 | 最大 30ms 程度 | クロック独立でバッファが増える（不変条件 4 に抵触） |

Discord 受信側の 40〜100ms は削れないので目標に含めない。

## B. 判定できないもの（回数を固定する）

**「声が似ているか」「自然に聞こえるか」は数値で判定できない。**
ここに「合格するまで止めるな」を適用すると無限ループになる。

| 対象 | 進め方 |
|---|---|
| 声質の似せ具合 | エポック 100 / 150 / 200 の重みを聴き比べ、**一番良いものを採用して終わり**。「もっと良くなるかも」で回し続けない |
| 音の自然さ | 同上。ただし下の代理指標に落とせるものは落とす |

判定できる代理指標に落とせるものは落とす：

- 「途切れる」→ `under` / `drop` が 0 か（**数えられる**）
- 「ブツブツ鳴る」→ ブロック境界で不連続が出ていないか（**測れる**）
- 「遅い」→ `TOTAL` が何 ms か（**測れる**）
- 「こもる」→ `--extra-ms` を 100 → 200 にして変わるか（**A/B できる**）
- 「ピッチが揺れる」→ 窓が 10ms グリッドに乗っているか（**起動時に弾かれる**）

**残る「声が似ているか」だけが本当の主観判断。** ここは人間が聴いて決める。

## 権限の線引き

自律化するのは**工程**であって**権限**ではない。

| AI に任せる | 人間が承認する |
|---|---|
| 調べる・作る・直す・検証する | 消す・送る・払う・公開する・本番を変える |

このリポジトリでの具体的な線引き：

- ローカルファイルの削除 → **承認が要る**（`inventory_local.py` は読み取り専用）
- 音声モデルの学習素材の追加 → **承認が要る**（→ 声の権利）
- コードの修正・テストの追加・ドキュメント更新 → 任せてよい
